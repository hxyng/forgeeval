ForgeEval data model & infrastructure

ForgeEval captures LLM application traces, replays them against new prompt or model versions, scores the results, and blocks a pull request when a metric regresses. This page covers the normalized PostgreSQL schema, the ERD, and the single-region AWS deployment behind it.

Versions are immutable

Prompts, datasets and evaluators get a new *_versions row on every change. Runs point at exact versions, so a score from March can be reproduced in October.

Ingest is separate from scoring

The API only writes traces and enqueues work. Workers do the slow, failure-prone scoring. One run_items row per dataset item is the unit of retry.

JSONB only where shape varies

Model inputs/outputs, span attributes and evaluator configs are JSONB. Anything filtered, joined or aggregated (latency, cost, status, tokens) is a typed column.

Infrastructure

Single-region deployment on AWS

A simpler production story than Kubernetes: two ECS Fargate services behind one ALB, RDS for state, SQS with a dead-letter queue for jobs, S3 for large payloads. Everything is declared in Terraform and shipped by GitHub Actions. Locally, the same services run under Docker Compose with Redis Streams standing in for SQS and MinIO for S3.

Sequence

Ingest → queue → score

The hot path returns as soon as traces are durable. A replay or CI run fans out into one job per dataset item; the run finishes when every item has succeeded or been dead-lettered.

  SDK->>API: POST /v1/traces:batch (Idempotency-Key)
  API->>DB: INSERT traces ON CONFLICT (project_id, idempotency_key) DO NOTHING
  API-->>SDK: 202 Accepted {accepted, duplicates}

  SDK->>API: POST /v1/runs {dataset_version, prompt_version, evaluators, baseline_run}
  API->>DB: BEGIN · insert eval_runs + run_items (status=queued) · COMMIT
  API->>Q: SendMessageBatch(run_item ids)
  API-->>SDK: 201 {run_id}

  loop each message
    Q->>W: receive (visibility timeout 120s)
    W->>DB: UPDATE run_items SET status=leased, attempt=attempt+1 WHERE id=$1 AND status IN (queued, retry_wait)
    W->>J: generate with candidate prompt, then rubric score
    W->>DB: upsert scores (run_item_id, evaluator_version_id) · status=succeeded
    W->>Q: DeleteMessage
  end

  SDK->>API: GET /v1/gates/{gate_id}/check?run_id=…
  API->>DB: aggregate scores vs baseline · insert gate_checks
  API-->>SDK: {verdict: fail, metric: rubric_helpfulness, delta: -0.07}

Table reference

Tables by domain

Every table has created_at timestamptz NOT NULL DEFAULT now(); it is omitted below unless it matters. IDs are UUIDv7 so they sort by insert time and index well.

Failure model

Run item lifecycle

run_items.status is the explicit state machine the workers enforce. Each transition is a single conditional UPDATE … WHERE status IN (…), so a duplicate SQS delivery loses the race and exits without side effects. Run status is derived from item counts.

stateDiagram-v2
  [*] --> queued
  queued --> leased: worker claims
  retry_wait --> leased: next_attempt_at reached
  leased --> succeeded: all scores written
  leased --> retry_wait: transient error, attempt < 5
  leased --> retry_wait: lease expired (timeout)
  leased --> dead_lettered: attempt = 5 or permanent error
  queued --> cancelled: run cancelled
  retry_wait --> cancelled: run cancelled
  dead_lettered --> queued: manual replay
  succeeded --> [*]
  cancelled --> [*]
eval_runs.statusCondition
queuedCreated, no item leased yet
runningAt least one item leased or retrying
succeededEvery item succeeded
partialAll items terminal, some dead-lettered, failed share ≤ max_failure_ratio
failedAll items terminal and failed share above the ratio, or the run errored before fan-out
cancelledUser or CI cancelled; in-flight items finish, queued ones are skipped
Backoff: min(2^attempt × 2s, 120s) plus full jitter. Permanent errors (schema mismatch, 4xx from the judge model) skip retries and go straight to dead_lettered.
Constraints that carry the design

Integrity rules

Idempotent ingest

UNIQUE (project_id, idempotency_key) on traces. The SDK derives the key from its own trace id, so a retried batch inserts nothing new and the API reports the duplicates.

Exactly one score per evaluator per item

UNIQUE (run_item_id, evaluator_version_id) on scores, written with ON CONFLICT DO UPDATE. Redelivered jobs overwrite rather than double-count.

Frozen versions

A trigger rejects UPDATE on dataset_items once its dataset_versions.frozen_at is set, and on any *_versions row referenced by a run. Edits create a new version.

Comparable baselines

A check constraint in the run-creation transaction requires baseline_run_id to share the same dataset_version_id. Comparing runs over different data is a 422.

Tenant isolation

Every query is scoped by project_id, taken from the API key and never from the request body. Postgres row-level security on project_id is the backstop.

Secrets never stored in plain text

API keys are stored as key_prefix plus an HMAC-SHA256 key_hash. Redaction runs in the SDK before upload; traces.redaction records which rules fired.

Interview prompt: what changes at 10×

At 10× scale

  • Partition traces and spans by month on started_at with pg_partman, and drop old partitions per retention policy instead of running large deletes.
  • Move span analytics to a columnar store such as ClickHouse when dashboard queries start competing with OLTP writes. Postgres keeps the run and score tables.
  • Pre-aggregate run metrics into a run_metrics table when a run finishes, so gate checks and comparisons stop scanning scores.
  • Split queues by evaluator cost. Cheap rule-based scoring and slow LLM rubric scoring get separate SQS queues and worker pools, so rubric backlogs don't delay CI gates.
  • Batch judge-model calls and cache rubric results keyed on (evaluator_version.config_hash, output hash) to cut cost per 1K traces.
