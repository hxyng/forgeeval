# ForgeEval on AWS (Terraform)

Single-region production environment: ECS Fargate behind an ALB, RDS PostgreSQL 16, SQS, S3, Secrets
Manager, ADOT tracing sidecars and CloudWatch alarms. Nothing here has been applied yet; the checks
below run offline (mocked provider), and a `plan` runs in CI once an AWS account is connected.

## Layout

| Path | What it is |
| --- | --- |
| `bootstrap/` | Run once, local state: remote-state bucket, GitHub OIDC provider, plan and deploy roles |
| `envs/prod/` | The environment: composes the modules below, S3 backend with `use_lockfile` |
| `modules/network` | VPC over 2 AZs, public and private subnets, optional NAT, security groups |
| `modules/data` | RDS PostgreSQL 16 or Aurora Serverless v2 (`database_engine`), SQS `eval-jobs` and DLQ, S3 payload bucket, Secrets Manager |
| `modules/alb` | Internet-facing ALB, listeners, target groups, path rules |
| `modules/compute` | ECR, ECS cluster, task definitions, services, worker autoscaling (target tracking, or step scaling for scale-to-zero), IAM |
| `modules/console` | Optional console hosting: private S3 bucket and CloudFront (OAC, SPA rewrite, API paths to the ALB); used with `console_hosting = "s3_cloudfront"` |
| `modules/observability` | SNS topic (own KMS key) and the six alarms (four while asleep) |
| `scripts/demo.sh` | Wake (`up`), sleep (`down`) and `status` for demo mode |
| `local/` | Emulator config for local development (not Terraform) |

```
internet -> ALB (80/443) -+-> /v1/*, /docs, /openapi.json, /healthz, /readyz -> api  (2 tasks, :8000)
                          +-> everything else                                -> web  (1 task,  :80)
SQS eval-jobs (+DLQ) <- api / worker -> RDS PostgreSQL (private subnets, TLS only)
worker (1..worker_max, scaled on queue backlog per task) -> S3 traces/ , model API
api / worker tasks each carry an ADOT collector sidecar: traces -> X-Ray, metrics -> CloudWatch (EMF)
```

Network modes, controlled by `enable_nat_gateway`:

- `false` (default, cheapest): tasks run in the public subnets with public IPs. The task security group
  admits only the ALB security group; there is no ingress from `0.0.0.0/0` anywhere except the ALB.
- `true`: tasks move to the private subnets behind one NAT gateway (about +$33/month plus data).

RDS is always in private subnets and only admits the task security group on 5432.

## First-time setup

Prerequisites: an AWS account, credentials with admin rights for the first two applies, Terraform 1.16.

```bash
# 1. State bucket + GitHub OIDC roles (local state, run once)
cd infra/bootstrap
terraform init
terraform apply            # review the plan first
terraform output           # state_bucket, plan_role_arn, deploy_role_arn

# 2. The environment
cd ../envs/prod
cp backend.hcl.example backend.hcl          # fill in the bucket from step 1
cp terraform.tfvars.example terraform.tfvars
terraform init -backend-config=backend.hcl
terraform apply
```

If the account already has the GitHub OIDC provider (only one per URL is allowed), pass
`-var existing_oidc_provider_arn=<arn>` to bootstrap. Bootstrap state is local; after the first apply
you may add an `s3` backend block pointing at the new bucket and run `terraform init -migrate-state`.

`name_prefix` (default `forgeeval-prod`) must be the same in `bootstrap` and `envs/prod`, because the
deploy role's permissions are written against the resource names the environment will create.

After the first apply the services cannot start (the ECR repositories are empty). That is expected:
set the repository variables and run the deploy workflow, see
[`docs/runbooks/deploy-and-rollback.md`](../docs/runbooks/deploy-and-rollback.md).

## Set the model API key

Terraform creates the secret and gives it a placeholder (ECS cannot start a task whose secret has no
value). Terraform never sees the real value and ignores later changes to it:

```bash
aws secretsmanager put-secret-value \
  --secret-id "$(terraform output -raw model_api_key_secret_name)" \
  --secret-string 'sk-...'
# secrets are read when a task starts: roll the services to pick the new value up
aws ecs update-service --cluster forgeeval-prod --service forgeeval-prod-worker --force-new-deployment
aws ecs update-service --cluster forgeeval-prod --service forgeeval-prod-api --force-new-deployment
```

Set `model_base_url` in `terraform.tfvars` if the endpoint is not the application default.
The API key pepper is generated by Terraform as an ephemeral value and written to Secrets Manager
through a write-only argument, so it is not stored in Terraform state.

## Demo mode: sleep at a few dollars a month, wake on demand

Two switches in `envs/prod` make a low-traffic or demo environment cheap without weakening anything:

- `active` (default `true`). `false` puts the environment to sleep: the ALB, its listeners, target
  groups and listener rules, the three ECS services, the worker autoscaling and the two alarms that read
  the ALB metrics are removed. Everything else stays: VPC and security groups, ECS cluster, task
  definitions, ECR repositories and images, SQS queue and DLQ, S3 bucket, secrets, IAM, log groups, the
  database and the queue and database alarms. Outputs that belong to removed resources
  (`alb_dns_name`, the three `*_service_name`s) become `null`.
- `database_engine` (default `"rds"`). `"aurora-serverless"` swaps the RDS instance for an Aurora
  PostgreSQL 16 Serverless v2 cluster with one `db.serverless` instance that scales to 0 ACU and pauses
  after `aurora_auto_pause_seconds` (default 300) without connections. **Changing the engine replaces
  the database**: choose it before the first apply (or migrate the data yourself).

```bash
infra/scripts/demo.sh up       # terraform apply -var active=true, then wait for /readyz through the ALB
infra/scripts/demo.sh down     # terraform apply -var active=false
infra/scripts/demo.sh status   # awake or asleep, running tasks, estimated $/hour
```

Extra arguments go to `terraform apply` (`demo.sh up -var-file=/abs/prod.tfvars`); pass the same ones to
`down`. The script needs terraform, the AWS CLI, curl and credentials; set `DEMO_AUTO_APPROVE=1` to skip
the apply confirmation.

### How `active = false` works, resource by resource

| Resource | Asleep | How |
| --- | --- | --- |
| `module.alb` (ALB, 2 listeners, 2 target groups, listener rule) | removed | `count = var.active ? 1 : 0` on the module |
| `aws_ecs_service` api, web, worker | removed | `count = var.services_enabled` |
| `aws_appautoscaling_target` and `_policy` (worker) | removed | same `count` |
| `terraform_data.alb_ready` (listener wait) | removed | same `count` |
| Alarms `alb_5xx_rate`, `api_unhealthy_targets` | removed | `count = var.alb_enabled` in observability |
| ECS cluster, 4 task definitions, ECR, log groups, IAM | kept | not parameterised by `active` |
| Database, queues, bucket, secrets, queue and DB alarms | kept | the `data` module does not receive `active` |

The tests assert that the persistent resources do not change between `active = true` and `false`
(`persistent_state` output compared across runs, `task_definition_fingerprints` in the compute tests).
Resources whose address gained a `[0]` carry `moved` blocks, so upgrading an existing environment plans
no replacement of the ALB, services or RDS instance.

Two consequences worth knowing. The web task's `API_UPSTREAM` fallback no longer points at the ALB DNS
name: the name changes whenever the ALB is recreated, and keeping it would have made the task
definition depend on `active`. The ALB already routes `/v1/*` to the API, so the fallback is never
used in AWS; it now defaults to `http://127.0.0.1:8000` (`api_upstream`). And while asleep,
`deploy.yml` skips with a notice instead of failing (there is no service to migrate or roll).

### Services start from the latest deployed image

Terraform registers the task definitions with the tag `bootstrap`, and `deploy.yml` registers a newer
revision per commit while the services use `ignore_changes = [task_definition]`. A service created by
waking up must not start from the `bootstrap` revision (it names an image tag that does not exist), so
`modules/compute` looks each family up with

```hcl
data "aws_ecs_task_definition" "latest" {
  for_each        = local.running_services
  task_definition = aws_ecs_task_definition.this[each.key].family   # family only: newest ACTIVE revision
}
```

and creates each service from `data.aws_ecs_task_definition.latest[...].arn`. ECS resolves a bare family
name to its latest ACTIVE revision, which is whatever the last deploy registered (old revisions stay
ACTIVE because of `skip_destroy`). A service that already exists ignores the value, so day-to-day
applies are unchanged. If you change task-definition settings in Terraform, Terraform registers a new
revision and the next wake-up picks up that revision (image tag `bootstrap`): run the deploy workflow
after such a change and before sleeping, so the newest revision carries a real image.

### Database cold start

Aurora needs about 15 seconds to resume from 0 ACU (AWS documents "approximately 15 seconds"), and 30
seconds or more if it was paused for over a day. The first request after a pause, and the first `up`,
therefore wait for the database: `/readyz` fails its ALB health check until a connection works. With
`database_engine = "aurora-serverless"` the services' `health_check_grace_period_seconds` is 180 for the
API (90 with RDS) and 120 for web (60 with RDS), so ECS does not kill tasks that are only waiting for the
database. The backend sets no connect timeout, so the connection simply waits. Aurora does not pause
while any connection is open, and an RDS Proxy would also prevent pausing, so none is used.

### Aurora settings

| Setting | Value |
| --- | --- |
| Engine | `aurora-postgresql`, `aurora_engine_version` default `16.6`. Scaling to 0 ACU needs 16.3 or newer; a validation enforces it |
| Capacity | `min_capacity = 0`, `max_capacity = aurora_max_acu` (default 2), `seconds_until_auto_pause = aurora_auto_pause_seconds` (default 300; AWS allows 300 to 86400) |
| Instances | one `db.serverless` writer, not publicly accessible, private subnets, same security group |
| Security | storage encrypted, `manage_master_user_password = true`, cluster parameter group with `rds.force_ssl = 1`, IAM database authentication on |
| Backups | 7 days; `deletion_protection` and the final snapshot follow the existing variables |
| Alarms | CPU on the instance, as for RDS. `ACUUtilization` (above 90% of the maximum for 10 minutes) replaces `FreeStorageSpace`, which does not apply because Aurora storage grows on its own. `ACUUtilization` reports 0 while paused, so the alarm stays quiet |

## Lean always-on: about $62 a month instead of $107

Six opt-in variables in `envs/prod` cut the always-on bill without removing the ALB, the database or any
security control. Every default keeps today's behaviour (the tests assert it). Ready-made `terraform.tfvars`:

```hcl
cpu_architecture   = "ARM64"          # Graviton: about 20% cheaper Fargate
worker_capacity    = "FARGATE_SPOT"   # worker only; api and web stay on-demand
worker_min_count   = 0                # scale to zero when the queue is empty
api_desired_count  = 1                # 2 keeps HA, see below
console_hosting    = "s3_cloudfront"  # no web task: static files on S3 behind CloudFront
container_insights = false            # drop per-task metrics; traces and EMF metrics stay
```

If you use `console_hosting = "s3_cloudfront"` also set `console_hosting` in `bootstrap` (and apply it), so the
deploy role may upload to the console bucket, see [the deploy workflow](#deploy-workflow-changes).

| Variable | Values (default first) | What it does | Trade-off |
| --- | --- | --- | --- |
| `cpu_architecture` | `X86_64`, `ARM64` | `runtime_platform` of all four task definitions. The deploy workflow reads it from the `api` task definition and builds `linux/arm64` images (tag suffix `-arm64`) | Builds run under QEMU on the x86 runner (slower). ADOT `v0.49.0` is multi-arch (checked: amd64 and arm64). In `us-east-1` the VPC skips zone `use1-az3`, where Fargate has no ARM64 capacity |
| `worker_capacity` | `FARGATE`, `FARGATE_SPOT` | Capacity provider strategy on the worker service only | Spot tasks get a two-minute warning (SIGTERM, then SIGKILL after `stopTimeout` = 120 s). The worker handles SIGTERM and SQS redelivers an unacknowledged message after the 120 s visibility timeout ([ADR 0001](../docs/adr/0001-job-queue.md)). Fargate never falls back to on-demand: when Spot capacity is short, jobs wait |
| `worker_min_count` | `1`, `0` to `worker_max` | Minimum worker tasks | At 0 the first job waits for a task to start (about one to two minutes, unmeasured) |
| `api_desired_count` | `2`, `1` | API tasks | With 1, a failed task or a deploy leaves a gap: ECS replaces the task in about one to two minutes (unmeasured), during which the ALB has no healthy target. With 2 (one per zone) a single failure is invisible and rolling deploys keep capacity. Save about $12 for the single point of failure |
| `console_hosting` | `ecs`, `s3_cloudfront` | Where the console is served from | See below |
| `container_insights` | `true`, `false` | Container Insights on the cluster | No per-task CPU and memory dashboards (basic ECS metrics stay). X-Ray traces and the application's EMF metrics are unaffected |

### Worker scale-to-zero

With `worker_min_count = 0` (or `container_insights = false`) the target-tracking policy is replaced by step
scaling in `modules/compute/scaling.tf`. The reason is concrete: the target-tracking expression divides the
SQS backlog by `ECS/ContainerInsights RunningTaskCount`, a metric that only exists with Container Insights
on and has no datapoints while 0 tasks run, so it could neither start the first worker nor survive Insights
being off. The step policy needs only SQS metrics, which SQS publishes whether or not a worker exists:

- alarm `worker-backlog`: at least one visible message for one minute adds 1 worker (backlog under 10), 2
  (10 to 49) or 4 (50 or more), 120 s cooldown, capped by `worker_max`. Application Auto Scaling may raise
  the desired count from 0 because the target's `min_capacity` is 0.
- alarm `worker-idle`: nothing visible and nothing in flight for `worker_idle_minutes` (10) returns the
  count to `worker_min_count` (an exact capacity, not a decrement). A busy worker is therefore never scaled
  in; with Spot it only disappears when AWS reclaims it.
- Unlike target tracking, step scaling does not size the fleet proportionally to the backlog: it adds
  workers in steps while a backlog persists.

### Console on S3 and CloudFront

`console_hosting = "s3_cloudfront"` removes the `web` ECS service, task definition, log group and ALB target
group (unmatched ALB paths answer 404) and adds `modules/console`:

- a private S3 bucket `<name_prefix>-console-<account id>` (all four public-access blocks, SSE-S3, TLS-only
  policy) readable only by this distribution through Origin Access Control (`AWS:SourceArn` condition);
- one CloudFront distribution, `PriceClass_100`, HTTPS only for viewers. Default behaviour: the bucket.
  Behaviours for `/v1/*`, `/docs` and `/openapi.json`: the ALB (all methods, no caching, every viewer header
  forwarded), so the console stays same-origin and the API needs no CORS;
- a viewer-request CloudFront Function on the console behaviour rewrites extensionless paths to
  `/index.html` (SPA routing). It deliberately replaces the usual 403/404 custom error response: that is
  distribution-wide, so it would also turn the API's own 403 and 404 answers into a `200` HTML page.
- cache headers are set by the deploy workflow: `assets/*` (hashed) `public, max-age=31536000, immutable`,
  `index.html` `no-cache`, other files one hour.

Constraints: CloudFront reaches the ALB over **HTTP** (the ALB has no certificate for its own DNS name), so
that hop crosses the internet unencrypted, and the ALB stays directly reachable as it is today. Setting
`acm_certificate_arn` together with `s3_cloudfront` is rejected: the HTTP listener would redirect and the
origin would fail. Attach a domain and certificate to CloudFront instead if that matters. Trivy flags the
missing WAF and access logging on the distribution (see `.trivyignore.yaml`).

### Interaction with demo mode

`active = false` still removes the ALB, listeners and all ECS services, the worker autoscaling and the new
scaling alarms. The bucket and the distribution persist (tests assert the persistent set is identical awake
and asleep). While asleep the console still loads from the edge, the API origin is `asleep.invalid`, which
never resolves, so `/v1/*` answers 502. Each wake-up creates a new ALB, so `demo.sh up` also updates the
distribution's API origin; CloudFront needs a few minutes to deploy that. At rest the bucket and distribution
cost about $0 (CloudFront has no hourly fee, storage is a few MB, estimate).

### Deploy workflow changes

`deploy.yml` stays one workflow:

- it reads `runtimePlatform.cpuArchitecture` from the `api` task definition and builds with
  `docker buildx build --platform linux/arm64 --provenance=false --push` (QEMU is set up only then), so the
  deploy and the task definitions cannot disagree. ARM64 images use the tag `<sha>-arm64`, so re-running a
  commit after switching architecture never reuses the other architecture's immutable tag;
- repository variable `CONSOLE_HOSTING` (default `ecs`). With `s3_cloudfront` it builds no web image,
  registers and rolls only `api` and `worker`, runs `pnpm install --frozen-lockfile && pnpm build`,
  syncs `web/dist` to the bucket (assets first, `index.html` last) and invalidates `/*`. It needs the
  repository variable `CLOUDFRONT_DISTRIBUTION_ID` (`terraform output cloudfront_distribution_id`); set
  `APP_URL` to `terraform output app_url` so the smoke test also checks `/` and `/openapi.json` through
  CloudFront (the ALB's `/readyz` is always checked directly).
- `bootstrap` variable `console_hosting = "s3_cloudfront"` adds to the deploy role exactly: `s3:ListBucket` and
  `s3:GetBucketLocation` on the console bucket, `s3:PutObject` and `s3:DeleteObject` on its objects, and
  `cloudfront:CreateInvalidation` and `GetInvalidation` on this account's distributions (the ID does not
  exist yet when bootstrap runs). Nothing changes with the default.

## Operational notes

- **Task definitions**: Terraform creates them with the placeholder tag `bootstrap`, and the services
  ignore later task-definition changes. `.github/workflows/deploy.yml` registers a revision per commit.
  After changing task-definition settings in Terraform (environment, secrets, sizes), run the deploy
  workflow to roll the change out. Old revisions are kept (`skip_destroy`) so rollback stays possible.
  Services created by demo-mode wake-up start from the latest ACTIVE revision (see Demo mode).
- **Database credentials rotate** (RDS-managed master secret, every 7 days by default), and ECS
  injects secrets only when a task starts. So the long-running api and worker tasks don't get the
  password injected: they receive `DB_SECRET_ARN` and read the secret for each new connection
  (cached 5 minutes, re-read immediately if Postgres rejects the password; see
  `backend/forgeeval/db/credentials.py`). Their task roles may `GetSecretValue` on that one secret.
  The short-lived `migrate` task still gets credentials injected at start, which is safe for a task
  that lives seconds.
- **Worker scaling** uses a target-tracking metric-math expression (visible messages divided by running
  tasks, target 10); validate its behaviour under real load.
- **ECS Exec** is off. `enable_ecs_exec = true` turns it on and adds the SSM permissions to the task roles.
- **HTTPS**: set `acm_certificate_arn` (certificate in the same region); HTTP then redirects to HTTPS.
  DNS is not managed here: point your domain at `alb_dns_name`.
- **Migrate task** has no collector sidecar so it exits when `alembic upgrade head` finishes.

## Teardown

```bash
cd infra/envs/prod
# 1. RDS refuses deletion while protected; the force flag lets destroy remove the non-empty
#    payload bucket and the ECR repositories (this deletes eval payloads and images).
terraform apply -var deletion_protection=false -var teardown_force_delete=true
# 2. Remove everything
terraform destroy -var deletion_protection=false -var teardown_force_delete=true
```

The database takes a final snapshot (`<prefix>-db-final`) before it is deleted; delete that snapshot
yourself if you do not want it (and its cost). Secrets are scheduled for deletion with a 7-day recovery
window. Finally run `terraform destroy` in `infra/bootstrap` after deleting all object versions in the
state bucket (it is versioned).
