# ForgeEval on AWS (Terraform)

Single-region production environment: ECS Fargate behind an ALB, RDS PostgreSQL 16, SQS, S3, Secrets
Manager, ADOT tracing sidecars and CloudWatch alarms. Nothing here has been applied yet; the checks
below run offline (mocked provider), and a `plan` runs in CI once an AWS account is connected.

## Layout

| Path | What it is |
| --- | --- |
| `bootstrap/` | Run once, local state: remote-state bucket, GitHub OIDC provider, plan and deploy roles |
| `envs/prod/` | The environment: composes the modules below, S3 backend with `use_lockfile` |
| `modules/network` | VPC over 2 AZs, public and private subnets, optional NAT, security groups |
| `modules/data` | RDS PostgreSQL 16, SQS `eval-jobs` and DLQ, S3 payload bucket, Secrets Manager |
| `modules/alb` | Internet-facing ALB, listeners, target groups, path rules |
| `modules/compute` | ECR, ECS cluster, task definitions, services, worker autoscaling, IAM |
| `modules/observability` | SNS topic (own KMS key) and the six alarms |
| `local/` | Emulator config for local development (not Terraform) |

```
internet -> ALB (80/443) -+-> /v1/*, /docs, /openapi.json, /healthz, /readyz -> api  (2 tasks, :8000)
                          +-> everything else                                -> web  (1 task,  :80)
SQS eval-jobs (+DLQ) <- api / worker -> RDS PostgreSQL (private subnets, TLS only)
worker (1..worker_max, scaled on queue backlog per task) -> S3 traces/ , model API
api / worker tasks each carry an ADOT collector sidecar: traces -> X-Ray, metrics -> CloudWatch (EMF)
```

Network modes, controlled by `enable_nat_gateway`:

- `false` (default, cheapest): tasks run in the public subnets with public IPs. The task security group
  admits only the ALB security group; there is no ingress from `0.0.0.0/0` anywhere except the ALB.
- `true`: tasks move to the private subnets behind one NAT gateway (about +$33/month plus data).

RDS is always in private subnets and only admits the task security group on 5432.

## First-time setup

Prerequisites: an AWS account, credentials with admin rights for the first two applies, Terraform 1.16.

```bash
# 1. State bucket + GitHub OIDC roles (local state, run once)
cd infra/bootstrap
terraform init
terraform apply            # review the plan first
terraform output           # state_bucket, plan_role_arn, deploy_role_arn

# 2. The environment
cd ../envs/prod
cp backend.hcl.example backend.hcl          # fill in the bucket from step 1
cp terraform.tfvars.example terraform.tfvars
terraform init -backend-config=backend.hcl
terraform apply
```

If the account already has the GitHub OIDC provider (only one per URL is allowed), pass
`-var existing_oidc_provider_arn=<arn>` to bootstrap. Bootstrap state is local; after the first apply
you may add an `s3` backend block pointing at the new bucket and run `terraform init -migrate-state`.

`name_prefix` (default `forgeeval-prod`) must be the same in `bootstrap` and `envs/prod`, because the
deploy role's permissions are written against the resource names the environment will create.

After the first apply the services cannot start (the ECR repositories are empty). That is expected:
set the repository variables and run the deploy workflow, see
[`docs/runbooks/deploy-and-rollback.md`](../docs/runbooks/deploy-and-rollback.md).

## Set the model API key

Terraform creates the secret and gives it a placeholder (ECS cannot start a task whose secret has no
value). Terraform never sees the real value and ignores later changes to it:

```bash
aws secretsmanager put-secret-value \
  --secret-id "$(terraform output -raw model_api_key_secret_name)" \
  --secret-string 'sk-...'
# secrets are read when a task starts: roll the services to pick the new value up
aws ecs update-service --cluster forgeeval-prod --service forgeeval-prod-worker --force-new-deployment
aws ecs update-service --cluster forgeeval-prod --service forgeeval-prod-api --force-new-deployment
```

Set `model_base_url` in `terraform.tfvars` if the endpoint is not the application default.
The API key pepper is generated by Terraform as an ephemeral value and written to Secrets Manager
through a write-only argument, so it is not stored in Terraform state.

## Checks (all run offline, no AWS account)

```bash
terraform fmt -check -recursive infra
( cd infra/envs/prod  && terraform init -backend=false && terraform validate && terraform test )
( cd infra/bootstrap  && terraform init -backend=false && terraform validate && terraform test )
for m in network data alb compute observability; do
  ( cd infra/modules/$m && terraform init -backend=false && terraform test ); done
( cd infra && tflint --init && tflint --recursive )
trivy config --skip-dirs '**/.terraform' --ignorefile infra/.trivyignore.yaml \
  --severity HIGH,CRITICAL --exit-code 1 infra
```

`terraform test` uses `mock_provider "aws"`: it checks what the configuration declares (security group
sources, RDS flags, queue redrive, bucket blocks, IAM scoping, the deploy role trust subject, network
placement per NAT mode), not what AWS does with it. The random provider is real because mocked
providers cannot serve ephemeral resources. `.trivyignore.yaml` lists each ignored Trivy check with its
justification.

Pinned: Terraform `~> 1.16` (tested with 1.16.4), AWS provider `~> 6.0` (locked at 6.68.0), random
`~> 3.7` (locked at 3.9.1), tflint 0.64.0 with the AWS ruleset 0.49.0, Trivy 0.74.0. The lock files in
`envs/prod` and `bootstrap` carry hashes for `linux_amd64` and `windows_amd64`.

## Monthly cost estimate (defaults, us-east-1)

1 web + 1 worker task running all month (worker not scaled out), x86 Fargate at $0.04048 per vCPU-hour
and $0.004445 per GB-hour, light traffic (about 1 ALB LCU), 5 GB of logs per month, no data transfer
out beyond the free allowance, no model API spend (that is billed by the model provider).

## Operational notes

- **Task definitions**: Terraform creates them with the placeholder tag `bootstrap`, and the services
  ignore later task-definition changes. `.github/workflows/deploy.yml` registers a revision per commit.
  After changing task-definition settings in Terraform (environment, secrets, sizes), run the deploy
  workflow to roll the change out. Old revisions are kept (`skip_destroy`) so rollback stays possible.
- **Database credentials rotate** (RDS-managed master secret, every 7 days by default), and ECS
  injects secrets only when a task starts. So the long-running api and worker tasks don't get the
  password injected: they receive `DB_SECRET_ARN` and read the secret for each new connection
  (cached 5 minutes, re-read immediately if Postgres rejects the password; see
  `backend/forgeeval/db/credentials.py`). Their task roles may `GetSecretValue` on that one secret.
  The short-lived `migrate` task still gets credentials injected at start, which is safe for a task
  that lives seconds.
- **Worker scaling** uses a target-tracking metric-math expression (visible messages divided by running
  tasks, target 10); validate its behaviour under real load.
- **ECS Exec** is off. `enable_ecs_exec = true` turns it on and adds the SSM permissions to the task roles.
- **HTTPS**: set `acm_certificate_arn` (certificate in the same region); HTTP then redirects to HTTPS.
  DNS is not managed here: point your domain at `alb_dns_name`.
- **Migrate task** has no collector sidecar so it exits when `alembic upgrade head` finishes.

## Teardown

```bash
cd infra/envs/prod
# 1. RDS refuses deletion while protected; the force flag lets destroy remove the non-empty
#    payload bucket and the ECR repositories (this deletes eval payloads and images).
terraform apply -var deletion_protection=false -var teardown_force_delete=true
# 2. Remove everything
terraform destroy -var deletion_protection=false -var teardown_force_delete=true
```

The database takes a final snapshot (`<prefix>-db-final`) before it is deleted; delete that snapshot
yourself if you do not want it (and its cost). Secrets are scheduled for deletion with a 7-day recovery
window. Finally run `terraform destroy` in `infra/bootstrap` after deleting all object versions in the
state bucket (it is versioned).
